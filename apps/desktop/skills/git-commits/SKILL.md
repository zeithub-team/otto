Хороший коммит объясняет **зачем**, а история читается как рассказ.

## Формат сообщения (Conventional Commits)
```
тип(область): краткое описание в повелительном наклонении

Что и зачем изменено — по делу, с причиной, а не пересказом диффа.
Ограничения, решения, на что обратить внимание.

Closes #123
```
- **Типы:** `feat` (новая возможность), `fix` (исправление), `refactor`, `perf`, `docs`, `test`, `build`, `ci`, `chore`, `style`. Ломающее изменение — `feat!:` или строка `BREAKING CHANGE: …`.
- **Заголовок** ≤ 72 символов, без точки; язык проекта (посмотри `git log`: если история на русском — пиши по-русски).
- **Тело** — по желанию, но обязательно для нетривиального: что было не так, почему выбрано это решение.

Хорошо: `fix(auth): не сбрасывать сессию при обновлении токена` — Плохо: `правки`, `fix bug`, `wip`, `изменения в файлах`.

## Как готовить коммиты
- Один коммит — одна логическая мысль, которая собирается и проходит тесты. Не смешивай форматирование, рефакторинг и новую функцию.
- Перед коммитом посмотри `git status` и `git diff`: нет ли лишнего (отладочные логи, `.env`, большие файлы, файлы агента/IDE).
- Секреты и сборочные артефакты в коммит не попадают (`.gitignore`).
- Не переписывай уже опубликованную историю без согласия; не делай `--force` в общую ветку.
- Ветки: `feat/…`, `fix/…`, короткие, от актуальной основной ветки.

## Pull request
**Заголовок** — как у коммита. **Описание:**
1. **Что и зачем** (проблема и решение в 2–4 строки).
2. **Как проверить** (шаги/команды, что ожидать).
3. **Риски и откат** (миграции, ломающие изменения, флаги).
4. **Скриншоты** для интерфейса (до/после).
5. Ссылки на задачи. Небольшой PR (до ~400 строк) ревьюят быстрее.

## Changelog
Группируй по типам: Добавлено / Исправлено / Изменено / Удалено; пиши для пользователя («Теперь можно…»), а не для разработчика. Версии по SemVer: `fix` → patch, `feat` → minor, ломающее → major.

## Когда просят написать сообщение
Прочитай реальный дифф (`git diff --staged` или файлы), определи тип и область, предложи заголовок и при необходимости тело. Не выдумывай того, чего в диффе нет. Не выполняй `git commit`/`push` без явной просьбы.
